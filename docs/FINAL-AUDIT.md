# Adversarial review against upstream guidance

Reviewed November 25, 2026, starting at `4d04bffd39c09960ab21c4da6c934f7e05786bd2`. Scope: all first-party application modules, save/checkpoint/recovery and transfer protocols, UI lifecycle, key/clipboard/generator handling, build/package/CI scripts, contributor documentation, templates and dependency provenance. This is a development review with targeted fault injection, not an independent certification, formal proof, hostile-file fuzzing campaign or guarantee that no defects remain.

Only fictional generated databases, synthetic factors, isolated drafts and the in-memory clipboard were used. No real vault, actual factor, account-protection file, user clipboard or native unlocked password-manager window was accessed. Existing working files and earlier portable previews were retained.

## Confirmed findings and fixes

Representative cases for the behavioral findings below were reproduced before their corresponding fixes. Regression failures were retained locally under ignored diagnostic output; the executable release excludes the tests and fault hooks.

| Finding | Impact | Resolution and evidence |
| --- | --- | --- |
| Field-level merging could combine one version's username with another's password or URL | High, credential correctness | Concurrent nonidentical edits to username/password/URL now require a decision for that entire bundle. App/File selects one actual version; Keep both retains the second complete version under a new UUID. Independent notes/custom fields still merge. Tests cover all three choices and draft recovery. |
| Successful decryption alone accepted a valid but stale save candidate | High, data preservation | Compare the reopened candidate with the intended tree, entry/history content, protected fields, cipher/KDF, custom metadata/icons and tombstones before publication. Apply the same content checks to creation, recovery copies and checkpoint components. Replayed valid saves/checkpoints fail without replacing the last good file or marking newer work protected. Retry succeeds. |
| Removing both optional pending-review components from a draft ZIP bypassed that review; duplicate components were ambiguous | Medium, recovery integrity | New working ciphertext authenticates the exact component inventory. Reject missing, duplicate, extra and unknown-format components. Retain original role/nonce/root checks. Valid legacy drafts remain readable but require an explicit older-format review; the next checkpoint writes the stronger format. |
| Keyboard/context copy from generator and conflict text bypassed clipboard ownership tracking; explicit copies lacked Windows exclusion formats | Medium, privacy | One bubbling copy handler covers text throughout the window, skips drag-only data and cancels a copy if protection cannot be attached. Explicit and normal copies attach Windows history/cloud exclusion formats. Synthetic events/payload checks verify ownership cleanup, zero DWORD flags and unchanged text, without touching the system clipboard. |
| A last-instant source writer using different key factors could fail transfer reconciliation without permanently blocking retry in that session | High, preservation | If the preserved source version cannot be opened/bound for pending review, block further publication. Retain the original working card and saved destination. Tests reopen the unique competing archive with its own fictional factors, reject retry, and checkpoint/lock successfully. |
| CLR probing could select a neighboring KeePass assembly before the embedded resolver ran | Medium, dependency hygiene | Startup refuses a nonembedded or wrong-version KeePass dependency before application/key handling. Separate negative processes verify both neighboring `KeePass.exe` and `KeePass.dll` are refused. This detects an unintended installation layout; it does not defend a writable executable folder against an attacker. |

UI workflows now have named, bounded diagnostic waits so an unhandled decision cannot hang contributor validation indefinitely. The Windows workflow remains manual and runs the same local validator. Private vulnerability reporting was enabled and its GitHub API state verified as enabled; no report was submitted.

## Comparison with primary sources

| Upstream guidance | KeePassHQ assessment |
| --- | --- |
| [KeePass synchronization](https://keepass.info/help/v2/sync.html) uses entry-level synchronization to avoid inconsistent credential combinations and merges histories. | KeePassHQ deliberately adds baseline-based field/order review around `MergeIn`. The credential bundle fix addresses the consequential combination risk. Independent notes remain a documented difference; this is not a claim of identical upstream synchronization semantics. Inspection of pinned `PwEntry.AssignProperties` confirmed that its `bIncludeHistory = false` call retains the already merged history. |
| [KeePass security](https://keepass.info/help/base/security.html) describes whole-database encryption, process-memory boundaries, closing the database on lock, and risks from executable URLs/placeholders. | KDBX cryptography stays in KeePass. Successful lock checkpoints private edits and releases models, keys, views and gates. Failed protection remains visibly incomplete. URL/command launching, placeholder expansion, plugins and auto-type are not invoked. WPF editing intentionally exposes expanded values and does not provide KeePass secure-desktop/control parity. |
| [KeePass master keys](https://keepass.info/help/base/keys.html) require every selected factor and recommend keeping key files separate from databases. | Preserve combined factors and key-file-only behavior; new password-backed files require confirmation. User guidance now makes separate factor storage and Windows-account recovery/portability limits explicit. Real account factors were not exercised. |
| [KDBX 4](https://keepass.info/help/kb/kdbx_4.html) documents authenticated encryption structure and configurable derivation. | Preserve pinned built-in AES/ChaCha20 and AES-KDF/Argon2 support. Creation keeps the existing AES-256/Argon2id defaults. Do not replace the crypto implementation or silently upgrade the dependency. Tests cover both cipher/KDF fixture families. |
| [Microsoft clipboard formats](https://learn.microsoft.com/en-us/windows/win32/dataxchg/clipboard-formats#cloud-clipboard-and-clipboard-history-formats) provides history/cloud exclusion formats. | Supply the exclusion marker and serialized zero DWORDs on copies. Payload construction/routing is tested; actual Windows history/cloud behavior is not tested through the prohibited user clipboard. Other software can ignore these formats. |
| [Microsoft assembly loading](https://learn.microsoft.com/en-us/dotnet/framework/deployment/how-the-runtime-locates-assemblies) describes default probing. | Build-time embedded hash verification is now accompanied by startup refusal of neighboring assemblies. Use a trusted, separate portable folder. |
| [KeePass integrity](https://keepass.info/integrity.html) and [security-issue analysis](https://keepass.info/help/kb/sec_issues.html) document upstream distribution hashes and threat analysis. | Documented 2.62 portable/source archive hashes match the published values. The included managed assembly still has the exact pinned hash and a valid Dominik Reichl Authenticode signature. The distinct corresponding-source mirror hash, GPL notices and Bootstrap MIT sources remain intact. No dependency upgrade or exhaustive vulnerability assessment is claimed. |

The pinned source also shows that KDBX writing normalizes standard-field protection using the database policy, and loading resets that in-memory policy to KeePass defaults. Readback/transfer checks account for this upstream behavior while checking stored field flags. XML newline normalization is accepted for unprotected text; protected passwords/custom fields must still match exactly, including whitespace. A regression rejects a CR/LF change in a protected password. Retaining other clients' metadata does not mean that KeePassHQ enforces every KeePass UI/application policy, such as scheduled master-key changes.

## Material limits

The wrapper is unsigned and this review is not independent assurance. Physical pointer/DPI/accessibility combinations, actual Windows clipboard behavior, real account factors and live sync-provider propagation require separate owner-controlled environment tests. No parser fuzzing, malicious KDF resource-exhaustion sandbox, crash/power-loss campaign or all-filesystem certification was performed.

Cross-file commits remain sequential and can leave duplicates. File/provider failures, compromised machines/install folders, remote edits not yet synchronized and later external deletions remain outside local guarantees. Managed strings, pagefiles, dumps and clipboard history have no forensic erasure guarantee. Clipboard ownership uses a matching-content digest and a non-atomic read/clear; identical replacement text cannot be distinguished, and a busy clipboard after process exit cannot be retried.

Older draft formats cannot retroactively authenticate an inventory they never stored. Their explicit compatibility review is intentional; new checkpoints provide the stronger binding. Authentic complete older checkpoints can also be replayed by someone controlling the draft directory; no external anti-rollback authority or freshness guarantee is claimed. Preserve encrypted originals/backups and review recovery choices. Noneditable history/settings/policies and opaque plugin conventions retain the limits documented in [FEATURES.md](../FEATURES.md) and [SECURITY.md](../SECURITY.md).
